## Parallel Codex worktrees

- Ordinary task work uses one pre-created isolated worktree and one foreground
  Codex owner session. A sole owner does not need a descriptor, claim, or memory
  project; transcript/resume, live Git, and committed task-local plans or notes
  carry working context.
- Invoke `orchestrating-parallel-worktrees` only for two or more writer sessions
  or when `.superpowers/parallel/session.conf` already exists. Explicit
  multi-writer work names file ownership, dependencies, an integration owner,
  and reconciliation order before launch.
- During all worktree workflows, the Codex session's startup checkout is its
  only implementation root. A primary-checkout `COORDINATOR_ONLY` session may
  create only the approved plan and descriptor in a new unclaimed linked
  worktree; it must not implement there through `workdir`, `git -C`, or absolute
  paths.
- New descriptors use schema v2 without memory fields. Existing schema-v1
  descriptors remain accepted through guard, claim, launch, resume, report,
  handoff, and release so active work is not stranded. Their legacy memory keys
  are structural compatibility data only and are never injected into Codex.
- The named `parallel-work` profile disables the Engram shell plugin and keeps
  the Engram MCP server enabled while preserving model, reasoning, and
  service-tier defaults. The helper launches directly with
  `codex -p parallel-work -C <root>`.
- Historical correction: task-project environment and MCP injection isolated
  explicit or manual MCP calls, but did not isolate automatic session
  registration, prompts, passive capture, or summaries. The 2026-08-13
  LEA-146/LEA-253/LEA-265 interleaving therefore cannot be repaired by treating
  a per-task Engram project as the session boundary.
- Engram remains supplementary ADR/decision memory, including verified durable
  lessons; ctx supplies original discussions, commands, rejected approaches,
  and source-session provenance. Current code, tests, specifications, and
  accepted ADRs remain authoritative. Do not load broad project history as task
  recovery, delete existing history, or blindly merge projects.
- Engram MCP startup instructions may request proactive saves and concise
  summaries even though shell-plugin prompt/recovery/passive hooks are disabled.
  A first write registers the actual runtime thread ID and physical startup
  directory, then uses the returned project plus explicit session identity for
  attribution. This is not an ownership, isolation, or readiness boundary.
- Live Git plus the descriptor and owner claim control explicit multi-writer
  writes. The owner claim is cooperative rather than an operating-system ACL;
  every participant must obey handoff and release boundaries.
- After compaction or resume, reconcile the physical root, branch, HEAD, dirty
  state, active task, and owned mutable artifacts. Prepared multi-writer sessions
  additionally repeat guard and claim. Memory and transcript labels never
  override live state.
- No tmux worker feature was added; visibility remains a caller concern and the
  completion report remains the machine-readable lifecycle contract.
- Build generated verification wrappers for their declared interpreter. In
  zsh, `status` is read-only and `path` is tied to `PATH`; use descriptive
  variables such as `git_status_text` and `changed_paths_text`, and invoke Bash
  explicitly for Bash-specific multiline wrappers. A thin parallel pilot
  reproduced the `status` collision in two independent writers.
- Creating a Stow link is a separate activation action. Once an installed file
  already links to tracked source, editing or integrating that source updates
  the live installed file immediately. Before defining approval gates, inspect
  the target with `readlink` or `realpath` and compare source and live hashes;
  combine integration and effective activation approval or stage outside the
  live link. Ordinary checkpoint commits, push, and PR creation or updates may
  share one explicit delivery approval under the global policy. Provider canaries
  and cleanup require authorization beyond that bundle.
- The tracked active policy is `codex-config/.codex/AGENTS.md`, the opt-in skill
  is `codex-config/.codex/skills/orchestrating-parallel-worktrees/SKILL.md`, and
  the helper is its `scripts/worktree-session`. The original 2026-08-08
  orchestration design is historical context where it conflicts with those
  sources. Do not copy mutable session, claim, or dirty-worktree state into this
  file.

## ctx history retrieval

- Ctx is a narrow historical-forensics aid, not repository or ownership
  authority. Use it for original discussion, rejected approaches, regressions,
  exact prior commands, and source-session provenance. Start from concrete
  identifiers with a small result limit; use `--primary-only` for user intent
  and decision provenance, but retain primary plus subagent results for
  implementation, test, and failure evidence.
- As of 2026-09-02, this machine uses the official managed ctx v1.3.1 binary and
  its installer-managed `ctx` agent skills. Automatic lexical indexing is on.
  Semantic retrieval and automatic binary upgrades are off through canonical
  `CTX_SEARCH_SEMANTIC=false` and `CTX_UPGRADE_AUTO=off` shell policy.
- Ctx v1 deliberately rejects symlinked mutable control files. Keep
  `~/.ctx/config.toml` as an owner-private regular local file and never put ctx
  config or private indexes back under Stow. The pre-v1 `work.sqlite` and the
  verified v0.25 recovery bundle under `~/.ctx/legacy-v0.25.0/` are inert,
  retained recovery data and require a separate cleanup decision.
- Keep `~/.config/opencode/skills` as a real local directory so ctx can safely
  update its OpenCode skill. Activate the optional package with
  `stow --no-folding opencode`; tracked skills remain leaf links while managed
  skills remain outside this repository.
- The first v1 Core publication indexed SoundCoaster history successfully and
  representative warmed lexical searches complete in roughly 0.1 seconds.
  Immutable active-plus-previous generations currently use about 19 GiB, which
  is the documented bounded recovery model rather than unbounded snapshots.
- Known upstream-bound import diagnostics remain: current Codex
  `item_completed` records are rejected when the authoritative `response_item`
  is available, and one healthy OpenCode `message.data` row is about 16.97 MB,
  above ctx's 16 MiB provider-value limit, so all 450 OpenCode sessions are
  currently absent from Core. Their canonical database and the pre-v1 index are
  retained; only two are SoundCoaster sessions. A later clean incremental
  refresh can make `ctx doctor` healthy because it reports the latest refresh,
  not the initial full-import diagnostics. Do not alter provider history or
  build a shadow import to hide this gap; reassess on a later upstream release.

## Shared Maestro tooling

- `maestro/` is selectively activated with no-folding Stow. The checked-in
  version/SHA256 manifest selects an official release installed outside Git in
  `~/.local/share/maestro-cli/<version>/`. See `docs/maestro.md` for setup,
  upgrade/rollback, privacy, and state ownership.
- `maestro-toolchain doctor --ios` checks prerequisites/inventory, never app or
  native-driver correctness. Project-owned flows still require explicit runtime
  ownership and exact installed build/JS-bundle identity.
- In Maestro 2.10.0, analytics/update opt-outs do not cover all automatic
  error/update requests. The shared local-testing launcher also overrides the
  Maestro API to loopback. It is not a network sandbox or cloud configuration.
- `maestro-mobile-testing` complements existing native regression/release skills;
  it does not mandate Maestro for every project or require Storybook for flows.

## Neovim and LazyVim

- `nvim/.config/nvim/lazyvim.json` is the source of truth for LazyVim extras.
  Do not duplicate those imports in `lua/config/lazy.lua`.
- Keep lazy.nvim's global `defaults.version` set to `false`. Neovim plugins do
  not all publish compatibility fixes as tagged releases; globally preferring
  tags selected Trouble 3.7.1 after Neovim 0.12 removed the Treesitter
  highlighter `_on_line` callback. Trouble's compatible implementation moved to
  `_on_range` on its main branch.
- Prefer LazyVim extra defaults over full local plugin configurations. Add only
  narrowly scoped options or keymaps so upstream fixes and integrations remain
  effective.
- Assign static `FZF_DEFAULT_OPTS` deterministically. Appending to an inherited
  value makes every nested interactive shell duplicate the same options.
- Snacks is the notification surface. A repeated notification may originate in
  another plugin's redraw or decoration provider; inspect the namespace and
  traceback before changing notifier settings.
- Current nvim-treesitter parsers belong under
  `~/.local/share/nvim/site/parser`. Legacy untracked `parser/` or
  `parser-info/` directories inside the plugin checkout can dirty the checkout
  and obstruct updates. Current nvim-treesitter maps the `jsonc` filetype to
  the `json` parser; an older standalone `jsonc.so` is not updateable by
  `TSUpdate` and should be removed only through an explicit cleanup gate.
- Install stable Neovim through Homebrew. Do not retain a parallel `HEAD` keg:
  it can remain linked to an older tree-sitter shared-library ABI after formula
  upgrades.
