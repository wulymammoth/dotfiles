### Stock native service blocker and superseded attempts

Cold native startup exposed another independent problem:
`Too many open files` while opening the rebuilt Core index. Live
`launchctl limit maxfiles` reports **256 / unlimited**; the shell used for
host diagnostics has **10,240 / unlimited**. Kernel limits remained
`kern.maxfilesperproc=92160` and `kern.maxfiles=184320`.

Two isolated, read-only ctx processes reproduced the boundary: a 256-file
soft limit made the index unavailable; 4,096 made it ready. This does not
require changing file permissions or the sandbox. The [1.4.1 resource helper](https://github.com/ctxrs/ctx/blob/v1.4.1/crates/ctx-history-platform/src/process_resources.rs)
already targets 4,096, but the [writer entry point](https://github.com/ctxrs/ctx/blob/v1.4.1/crates/ctx-history-index/src/writer_open.rs)
calls it after the cold recovery reader that fails.

A backed-up, ctx-only LaunchAgent experiment added
`SoftResourceLimits.NumberOfFiles=4096`. A subsequent fresh Codex connection
removed that customization while reconciling the service. This matches the
[native supervisor implementation](https://github.com/ctxrs/ctx/blob/v1.4.1/crates/ctx-daemon-runtime/src/supervisor/platform.rs):
it compares the entire plist against its maintained definition and writes
that definition on reinstall. The experiment did not change global resource
limits, and the maintained plist is back in place.

A subsequent administrator-authorized, ctx-only `launchctl debug` invocation
raised the daemon's soft file limit to 4,096 without altering global limits or
the maintained plist. The recovery helper preserved both the plist and the
private `supervisor-environment.json`: `ctx index mode manual` removes both,
so restoring only the plist is insufficient. Native startup then succeeded
(launchd PID and running ctx status both 84642). A fresh native Codex MCP
connection nevertheless reconciled that invocation away and returned to a
detached fallback. The one-time workaround therefore did not pass the
ownership-persistence check and is not a durable recovery procedure. Further
administrative startup experiments were stopped; historical retrieval remained
available through the configured MCP launcher.
The final full native MCP probe passed with a 256-file parent, including old
and recent searches and event inspection. After that ephemeral Codex process
closed, daemon status became `stopped`; continuous background indexing is
therefore not established. The publication receipt, file-limit canary, and a
concise final verification summary were copied to the private rollback
checkpoint for retention beyond the temporary diagnostic directory.

At that earlier checkpoint, MCP retrieval was recovered but native autostart
was not fixed. The final user-owned service above supersedes this checkpoint.
Automatic mode remains configured, and detached fallback daemons have
published fresh generations, but launchd ownership/handoff checks have failed.
A live PID or a successful search does not establish login/restart recovery.
Next work needs either an upstream change that raises the file limit before
Core recovery opens its index, or an explicitly approved broader launchd
resource adjustment that preserves existing kernel limits. The separately
identified macOS watcher fix in #964 also still awaits an official release.

## Findings

The following findings describe the initial investigation checkpoint.
There were two independent problems: sandbox access prevents ordinary CLI
retrieval, and the background daemon has stopped advancing the index. The
existing published index remains searchable with appropriate access.

### 1. Sandbox access produces a misleading index-verification failure

The initial installed versions were ctx **1.3.1** and Codex CLI **0.154.0**. The ctx
binary is a managed macOS ARM64 installation, with the matching installer
receipt and signed updater. The installed Codex ctx skill reports `current`.
Automatic indexing is enabled; semantic search and automatic binary upgrades
are disabled by the existing shell and ctx configuration.

Inside this session's workspace-write sandbox:

- `ctx status` reports `Search unavailable (generation verification failed)`.
- A focused `ctx search ... --refresh off` fails with `Failed to acquire
  Lockfile`, `PermissionDenied`, and `Operation not permitted`.
- Reading the history sources and index files is allowed. The missing
  permission is write-capable lock access, not basic history-file visibility.

The same historical search succeeds through an approved host execution.
Host `ctx status` reports a searchable generation with 2,344 sessions,
130,433 messages, and 225,404 tool calls.

Installed `ctx docs show storage` explicitly documents that lexical queries
open the existing Tantivy query lock with write-capable flags even when the
query makes no durable index change. `--refresh off` does not remove this
locking requirement.

Temporary native Codex sandbox probes, including managed configuration, gave
these results:

| Access/mode | Result |
| --- | --- |
| Default sandbox, search with `--refresh off` | Lock acquisition denied |
| Named workspace profile with write access only to `~/.ctx/search/lexical`, search with `--refresh off` | One expected historical result |
| Same narrow profile, `ctx status` | Search ready; refresh remains pending |
| Same narrow profile, normal background search | Fails establishing private daemon supervision under `~/.ctx/daemon` |
| Host-side local MCP server, `search` tool | One expected historical result |

The successful narrow probe used the installed CLI's `codex sandbox -P`
interface with a temporary named profile extending `:workspace`. Legacy
`sandbox_workspace_write.writable_roots` overrides did not provide a working
allowance in the direct sandbox probe. No persistent permission configuration
was changed.

### 2. The daemon is alive but history refresh has stalled

The last recorded heartbeat was **September 5, 2026, 15:49:58 EDT**. The active
generation pointer was last published at **15:49:17 EDT** that day. The
existing launchd-owned process, PID 56071 at investigation time, still runs
and holds its daemon identity.

A deterministic, content-free query returned an empty, terminal page for
Codex events in `[2026-09-06T00:00:00Z, 2026-09-13T00:00:00Z)`. There are
154 raw Codex rollout files in the September 6–12 date directories. This
establishes a real recent-history coverage gap independently of ranked
search wording. Raw history is still present.

A one-second native process sample found the main thread waiting in
`_pthread_join`/`__ulock_wait`, two `notify-rs fsevents loop` threads waiting
inside `CFRunLoopRun`, and the daemon-query thread still polling. This is a
strong match for the upstream macOS watcher stop/join race reported in
[ctx issue #957](https://github.com/ctxrs/ctx/issues/957). The triggering race
was not independently reproduced locally, so this identification remains an
evidence-backed diagnosis rather than a deterministic reproduction.

[PR #964](https://github.com/ctxrs/ctx/pull/964) merged on September 10 at
20:56:36 UTC and prepares the watcher fix for **1.4.2**. Its description
explicitly separates passing source tests from signed-release publication.
It also explains that a plain Cargo/source installation does not automatically
apply the official factory's dependency patch.

[Issue #958](https://github.com/ctxrs/ctx/issues/958) remains open. It describes
the related failure to recognize a stale heartbeat while a wedged daemon
continues to hold its advisory lock and answer lifecycle requests. Therefore
`Daemon running` alone is not adequate freshness evidence.

### 3. Version status and upgrade recommendation

At the time of this investigation:

| Surface | Version |
| --- | --- |
| Installed managed binary | 1.3.1 |
| Installed binary's signed stable update check and dry run | 1.3.2 |
| Latest published GitHub release and public changelog | 1.4.1, September 10 |
| Merged source fix for the observed watcher pattern | Prepared for 1.4.2 |

The [upstream changelog](https://ctx.rs/changelog/) documents the mandatory
**1.3.2 bridge**: the original update feed stops there, and later managed
versions use a newer feed. The local signed check and dry run confirmed this
first step. During approved execution, the 1.3.2 updater independently checked
the newer feed and confirmed the 1.4.1 target before applying it.

An update is warranted, but **1.4.1 does not include the merged 1.4.2 watcher
fix**. Use the official signed updater, recheck its target after the bridge,
and do not mistake a merged version bump for an available release. A restart
and fresh import can recover current availability; lasting prevention of the
identified watcher race requires an official build containing #964.
